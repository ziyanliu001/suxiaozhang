# 素食直播产销工坊模块技术架构与联调手册

> 本手册覆盖「素食直播产销协同」（live_factory）模块阶段一至阶段四的全部交付，
> 以及 2026-09-07 起《素食产销工坊升级与生态护城河演进计划书》里程碑 M0/M1
> 的落地（详见 2.7/3.4 节）。该模块与雨花公益食堂专区（受托记账/义工管理）
> 是**两套物理隔离的独立业务体系**：独立的角色/成员集合、独立的租户判定
> 字段、独立的前端页面树。阶段一至四全程零改动雨花公益专区任何既有表结构、
> 云函数逻辑或前端页面（`pages/profile/profile`、`pages/index/index` 仅做了
> 两处纯增量的入口挂载，详见「与雨花公益专区的边界」一节）。⚠️ 里程碑 M1
> 是这条边界线上**唯一一次刻意设计的跨越**：新增 `charity_contributions`
> 这一张中间账本集合 + `manageCharityContribution` 云函数（`redeem` action
> 会查雨花侧的 `user_roles`），`pages/profile/profile` 增量了一张反哺展示
> 卡片——两边仍然**不直接读写对方的私有集合**（工坊侧不碰 `report_logs`，
> 公益侧不碰 `tenant_members`/`production_orders`），只是通过这一张新集合
> 单向搭桥，不是推翻"物理隔离"这个设计原则。

## 1. 与雨花公益专区的边界

| 关注点 | 雨花公益专区 | live_factory 模块 |
|---|---|---|
| 成员/角色集合 | `user_roles` | `tenant_members`（物理隔离的独立集合，字段形状故意与 `user_roles` 保持一致，但绝不写入/读取 `user_roles`） |
| 角色鉴权入口 | `checkUserRole` 云函数、`AuthService` | 各云函数内联 `verifyTenantAccess(openid, tenantId, requiredRoles)`，直接查 `tenant_members` |
| 租户分类字段 | `tenants.orgType`（`yuhuazhai`/`elderly_canteen` 等，门店文化分类） | `tenants.businessType`/`entityType`/`paymentMode`（纯新增字段，与 `orgType` 语义完全独立，禁止互相推断） |
| 门店实体 | `stores` 集合 | 无对应实体——live_factory 是"一个租户 = 一个生产工作室"的单层模型，不生成 `stores` 文档 |

**为什么要强调物理隔离**：早期版本一度把 live_factory 的成员记录写进了 `user_roles`，
而雨花公益专区有约 50 个云函数用 `db.collection('user_roles').where({_openid}).limit(1)`
（不带角色过滤）解析"当前用户的雨花角色"。一个账号如果同时是雨花义工/店长又开通了
产销工坊，会被这些查询随机命中到错误的记录，导致雨花侧权限判断静默错乱。这是一个
真实修复过的问题，`tenant_members` 的独立集合设计就是它的根因修复方案，详见
`cloudfunctions/createProductionSpace/index.js` 头部注释与 `cloudfunctions/migrateLiveFactoryMembers`
迁移脚本。

## 2. 核心数据集合设计

### 2.1 `tenants`（复用雨花已有集合，新增字段）

`_id` 为云数据库自动生成，`tenantId`（业务主键，`lf_<timestamp36>_<rand4>` 格式）是
文档里的**普通字段**，不是 `_id`——查询必须用 `db.collection('tenants').where({tenantId})`，
不能 `.doc(tenantId)`（这是一个真实修复过的 bug，见下文状态机一节）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenantId` | string | 业务主键，`createProductionSpace` 生成 |
| `tenantName` | string | 工坊名称 |
| `businessType` | `'live_factory'` | 与雨花 `'charity_canteen'`/`'store_accounting'` 同一枚举，纯新增值 |
| `entityType` | `'individual'` | 目前仅支持个人手作坊零门槛开通 |
| `paymentMode` | `'none'` \| `'direct_wechat'` | 是否开启微信直连自动分账；默认 `'none'` |
| `settlementConfig` | `{producerRate, promoterRate}` | 选填，未配置时按 `createProductionOrder` 里的默认费率（制作方 85%、推广员 5%）兜底 |
| `status` | `'active'` | |

### 2.6 `order_settlements`（分账快照/红冲账本）

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenantId` / `orderId` | string | |
| `payAmount` / `producerAmount` / `promoterAmount` / `platformFee` | number | 恒等式：`producerAmount + promoterAmount + platformFee === payAmount`（整数分运算，`platformFee` 是余数，四舍五入损益永远吃进平台份额） |
| `producerRate` / `promoterRate` | number | ⚠️（2026-09-07 补充，此前手册遗漏）0~1 的比例，`buildSettlement` 时按 `tenants.settlementConfig` 快照定格——历史订单不受未来费率调整影响 |
| `settlementStatus` | `'unsettled'` \| `'settled'` \| `'refunded'` | |
| `isReversal` | boolean | `true` 表示这是一条红冲分录（金额为负），`originalSettlementId` 指回原记录（⚠️ 补充：仅红冲文档有这个字段） |
| `createdAt` | Date | ⚠️（2026-09-07 补充）分账快照创建时间 |
| `settledAt` / `settledBy` / `profitSharingOutOrderNo` | | |
| `refundedAt` | Date | ⚠️（2026-09-07 补充）`reverseSettlement` 原地标记 `refunded` 时写入 |

索引：`{tenantId:1, orderId:1}`、`{tenantId:1, settlementStatus:1}`。

### 2.7 `charity_contributions`（护城河一「以产养善」公益反哺账本，2026-09-07 新增）

工坊 `tenant_members` 体系与雨花公益 `user_roles` 体系之间唯一被设计出来的
中间账本——两边都只读写这一张集合，不直接查/改对方的私有集合（详见
`manageCharityContribution/index.js` 头部注释）。**架构决策：走内部账本
额度，不接入微信真实分账**——给"公益基金池"开一个真实分账接收方需要额外
的商户级注册、可能要做官方要求的敏感信息加密（本模块未实现），且分账
回退全链路空白（见 4.3 节），风险成本对一个可延迟核销的反哺功能不划算。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 确定性 `charity_${settlementId}`——同一笔分账记录只能转捐一次，`.add()` 撞重复直接失败，不需要额外唯一索引 |
| `tenantId` / `orderId` / `settlementId` | string | 关联来源订单与分账快照 |
| `sourceType` | `'profit_share'` | 目前只实现"利润转捐"这一种来源；`'direct_donation'`（工坊主直接对公捐赠，不经过某一笔订单）是计划书里标注的二期扩展项，未实现 |
| `amount` | number | 分，不超过来源分账记录的 `producerAmount` |
| `targetStoreId` / `targetStoreName` / `targetOrgType` | string | 目标门店只读引用 `stores` 集合；`targetStoreName`/`targetOrgType` 是 pledge 时点的快照，门店改名不会回填历史记录（与本项目其余快照字段同一惯例） |
| `pledgeStatus` | `'pledged'` → `'redeemed'` \| `'cancelled'` | `'cancelled'` 目前只是预留状态值，还没有任何云函数会把它写成这个值 |
| `pledgedBy` / `pledgedAt` | | |
| `redeemedBy` / `redeemedAt` / `redeemNote` | | |

索引：无需额外建（`_id` 已经是确定性主键；`tenantId`/`targetStoreId` 两条查询路径目前数据量级下全表扫描足够快，超出规模后再按需补 `{tenantId:1}`/`{targetStoreId:1}`）。

### 2.8 其余集合

- `workspace_invite_codes`：`{codeNormalized(唯一索引), tenantId, tenantName, role, createdBy, createdAt, expiresAt, usedBy, usedAt, qrFileID}`。
- `customer_checkins`：`{tenantId, buyerOpenId, streakCount, lastCheckinDate, lastOrderId}`，`{tenantId, buyerOpenId}` 唯一索引。
- `wxPayCore` 自有账本（与雨花订阅支付共用同一套支付基础设施）：`payment_orders`、`refund_orders`、`profit_sharing_orders`。

### 3.3.1 `markSettlementsSettled` 前端接入状态（✅ 已修复，2026-09-07，里程碑 M2）

此前（2026-09-06 及更早）云函数逻辑完整但全仓库没有任何前端页面调用它，
"批量确认线下结算"这个动作完全无法从小程序内触发。现已在 `settlement-summary`
页补上入口：`paymentMode !== 'direct_wechat'` 且存在待结算记录时，明细列表
每行"待结算"状态的订单前会出现勾选框（`ss-detail-order-group` 的
`bindtap="onToggleSelectOrder"`，勾选态是预算好的 `details[i].selected`
布尔字段，不在 WXML 里现场调用 `selectedOrderIds.indexOf(...)`——与
`pages/index/index.wxml` 的 `genRoleXxxDisabled` 历史修复同一个可靠性
考量），配合"全选待结算/清空"链接与"批量确认结算（N）"按钮，点击后
`wx.showModal` 二次确认才真正调用 `markSettlementsSettled`。

## 4. 关键业务流转状态机

### 4.1 `production_orders.orderStatus`

```
pending_payment ──(wxPayCore 支付成功回调)──▶ paid ──(completeProductionOrder)──▶ shipped
      │                                          │
      └──(wxPayCore 下单/支付失败)──▶ failed      └──(processProductionRefund)──▶ refunded（原状态需为 paid/in_production/shipped）
```

- `completeProductionOrder` 对 `shipped` 状态**幂等重入**：可重复调用补录/更正 `trackingNumber`，不会重复触发分账或发货通知（内部用调用前的状态判断"是否是这次调用真正完成的迁移"）。
- 状态机判断已抽成纯函数 `completeProductionOrder/lib/orderStatusMachine.js`（`canMarkShipped`），有独立单测。

### 4.2 排产算法（`liveFactoryCore/lib/scheduling.js`）

`assignProductionBatch`：

1. `quantity > dailyCapacityLimit` → 直接拒绝，不做跨日拆单。
2. 若传了 `preferredDate`（买家在预售日历选期下单）：
   - 早于 `orderCreateTime + leadTimeDays` → 拒绝。
   - 该日期产能不足 → **明确拒绝**，不静默改派到别的日期（买家选的是哪天，就该是哪天）。
3. 未传 `preferredDate` → 从最早可用日起逐日尝试，最多前瞻 `MAX_LOOKAHEAD_DAYS = 90` 天，售罄自动顺延。
4. 容量占用走 CAS（`production_capacity_counters` 的 `reserved: _.lte(limit - quantity)` 条件更新），并发安全，与 `createStore.reserveStoreQuota` 同一套模式。

### 4.3 分账时机（为什么不在支付成功瞬间分账）

```
支付成功 → buildSettlement（仅生成快照，status: unsettled，不动真钱）
标记发货 → tryAutoProfitSharing（direct_wechat 模式才真正调用微信支付分账 API）
```

刚付款就分账、买家马上退款，会撞上"分账回退失败"（微信支付分账回退需要接收方账户
有余额，链路复杂）。等订单真正发货（意味着不会随手取消）才分账，大幅降低这个窗口。
`agent_settlement`/`none` 模式不走自动分账，由 `markSettlementsSettled` 人工批量确认。

**已知残余风险**（如实标注，未实现）：发货后仍可能发生售后退款，若分账已完成，商户
账户"未分账余额"可能不足以覆盖退款。分账回退（`/v3/profitsharing/return-orders`）
的技术规范已归档在 `cloudfunctions/wxPayCore/lib/wxPayClient.js` 文件底部注释，
未编码实现。

### 4.4 `order_settlements.settlementStatus` 与红冲

```
unsettled ──(tryAutoProfitSharing 成功 / markSettlementsSettled)──▶ settled
unsettled ──(退款，mark_refunded 路径，原地标记，无新增分录)──▶ refunded
settled   ──(退款，create_reversal 路径，生成一条金额相反的新分录)──▶ 原记录不变 + 新增一条 isReversal:true 的红冲分录
```

净额计算（`bucketSettlements`/`buildDetailRows`/`computeOpsStats` 共用同一套配对逻辑）：
`settled` 记录若存在对应红冲分录，净额 = 原金额 + 红冲金额（红冲金额是负数），保证
"已结算后又退款"的订单不会一直虚高显示。

### 4.5 订阅消息通知

```
买家支付成功 → wx.requestSubscribeMessage 唤起"发货通知"订阅授权（前端，静默降级）
工坊标记发货（首次转 shipped 时）→ cloud.openapi.subscribeMessage.send 推送（后端，静默降级）
liveFactorySettlementCron 每日扫描（🆕 2026-09-07，里程碑 M2）→ 发现某租户有待人工确认的
未结算记录 → 向 space_owner 推送"待办提醒"（24 小时冷却，静默降级）
```

三条通知**各自需要独立申请真实模板 ID**（详见第 5 节）。任一环节失败（未授权/模板未配置/
发送异常）都不影响订单已标记发货、或分账扫描本身已经落库的事实。
