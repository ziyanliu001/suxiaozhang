## 一、目标设计（尚未实现，规划中）

### 1.1 三空间定位规范（构想）

- **雨花专区**（`yuhuazhai`）：受托记账、公信力锚点、全功能永久免费（白名单制）。
- **民间斋堂**（构想字段值 `independent`）：独立记账、单店永久免费，多店/批量导出等高阶功能采用"公益共担码"抵扣云存储算力，防止云资源被单向无限消耗。
- **产销工坊**（`workshop`）：商业造血闭环、日产能排单（防超卖与品控崩塌）、微信原生分账（无资金池合规模型）、买货即行善。

## 二、当前真实实现（已验证，供对照）

### 2.1 空间隔离的真实字段——不存在 `tenantType`，也不存在"三空间"三分类

- 全仓库 grep 确认：`tenantType`、`licenseCode`、`independent`（作为机构/组织类型取值）**均不存在**于 `cloudfunctions/` 与 `miniprogram/` 任何文件。
- 真实的组织分类字段是 **`orgType`**，且是**门店级字段**（不是机构/租户级），权威七值枚举（`docs/SCHEMA.md` 1.2 节）：`yuhuazhai` / `elderly_canteen` / `volunteer_station` / `rescue_team` / `tongxin_children` / `tongxin_cancer_care` / `other`。同一个 `tenantId` 下可以同时存在多个 `orgType` 的门店，不是"一个机构=一个空间类型"的排他分类。
- ⚠️ **「雨花专区」与「民间斋堂」在当前数据模型里没有独立区分字段**（`CLAUDE.md` 第 2 节已明确记录此历史术语澄清）：两者共享同一套 `stores` + `user_roles` 体系，区分目前只停留在产品文案层面。第一部分图里"雨花专区 vs 民间斋堂"两条独立空间路径，在当前代码里其实是**同一条路径**，靠 `orgType==='yuhuazhai'` 这一个布尔判断分叉，不是两套独立的租户体系。
- 真正有区分力的租户级标记只有 **`tenants.businessType === 'live_factory'`**（产销工坊），且该类租户不创建 `stores` 文档（一个租户即一个生产工作室，无多门店语义）——与图里"产销工坊"这一空间对应，但"雨花专区/民间斋堂"两个空间在当前代码里合并为一个。

### 2.2 套餐/权限的真实机制——`checkTenantPermission` 不感知 `orgType`

- 付费套餐唯一真源是 `tenant_subscriptions` 集合（`planType`: `basic`/`pro`/`enterprise`），解锁方式是 `activationCode`（12 位激活码，`activateTenantSubscription` 云函数 `redeem` action），**不存在 `licenseCode` 这个字段/概念**。
- `checkTenantPermission` 云函数（`cloudfunctions/checkTenantPermission/index.js`）**完全没有、也不需要 `orgType`/`tenantType` 分支**——它只按 `tenantId` 查 `tenant_subscriptions`，不区分门店/机构的业态类型。
- 雨花斋的免费权益**不经过这个订阅系统**，而是通过两条独立的、与 `checkTenantPermission` 无关的代码路径分别实现：
  - 门店数量配额豁免：`cloudfunctions/createStore/index.js`（`isYuhuazhaiNewStore` 分支，在配额校验之前短路跳过）+ `processRoleAudit`/`manageTenantSubscription` 的同类分流；
  - 审计级 Excel 导出免拦截：`pages/statistics/statistics.ts` 的 `exportToExcel()`/`resolveIsYuhuazhaiStore()`。
- 2026-09-08 新增：个人中心"会员开通/续费管理"套餐弹窗（`pages/profile/enterprise/saasSubscriptionModal.wxml`）新增 `isYuhuazhai` 文案分支——**这只是展示文案层面的分流，不改变 `checkTenantPermission` 的鉴权矩阵**，多店汇总看板等真正的付费功能对雨花斋依旧没有免费旁路。详见 `docs/BUSINESS_MODEL.md`「会员开通/续费管理」套餐弹窗雨花斋公益文案分支一节。
- **本次明确决定不改动**：`checkTenantPermission` 不会新增 `orgType==='yuhuazhai'` 即"强制永久旗舰版、不校验 `expireAt`"的分支——这会把"雨花斋免费"从"若干个具体功能点各自独立豁免"变成"整个订阅鉴权矩阵对雨花斋失效"，扩大范围且未经业务确认，留待第一部分目标设计正式排期时再评估。

### 2.3 工坊真实分账机制——三方切分 + 手动认领反哺账本，不是四方固定比例自动分账

以下均来自《素食直播产销工坊模块技术架构与联调手册.md》2.6~2.7 节，本文档只做摘要，字段级细节以该文档为准：

- 分账快照集合是 `order_settlements`（不是 `sunshine_ledgers`），三方切分：`producerAmount`（工坊履约）+ `promoterAmount`（渠道推广）+ `platformFee`（平台技术服务费，含微信支付通道费），恒等式 `producerAmount + promoterAmount + platformFee === payAmount`。**没有第四方"定向反哺善款"的固定切分份额**。
- `producerRate`/`promoterRate` 是**按租户可配置**的（`tenants.settlementConfig`，`manageTenantSettlementConfig` 云函数维护），不是全局写死的常量。`settlement-agreement.ts` 页面展示的 75.00%（工坊，无推广时 95.00%）/ 20.00%（推广）/ 4.40%（平台）/ 0.60%（微信支付通道费）是**默认展示值**，不等同于第一部分图里的 70/15/12/3。
- 微信原生分账**不是默认开启的**：`paymentMode` 字段只有 `'none'`（默认，人工/代理结算）与 `'direct_wechat'`（自动分账）两个真实取值，工坊需要商家主动配置成 `'direct_wechat'` 才会调用微信 Profit Sharing 接口；`'none'` 模式下走 `markSettlementsSettled` 人工批量确认。
- **"以产养善"公益反哺已经有真实雏形**，但机制与第一部分图完全不同：`charity_contributions` 集合（`manageCharityContribution` 云函数，`pledge`/`redeem`/`list` 三个 action）——工坊主可以把某一笔 `order_settlements` 里的 `producerAmount`（金额不固定，不是订单总额的固定 12%）**手动认领（pledge）转捐**给某个目标雨花斋/公益门店，认领后由该门店**手动核销（redeem）**，全程走**内部账本额度记账**，**明确架构决策为不接入微信真实分账**（该文档 2.7 节原文："给'公益基金池'开一个真实分账接收方需要额外的商户级注册...分账回退全链路空白...风险成本对一个可延迟核销的反哺功能不划算"）。也就是说，反哺不是自动 Webhook 触发的资金流转，而是一笔**记账层面的认领承诺**。

### 2.4 阳光账本/善缘墙真实机制——读时聚合，不是独立集合

- `getSunshineLedger` 云函数是**读时聚合**：查询 `report_logs`（捐赠/收支记录）、`volunteer_duty_logs`（义工工时）、`stores`/`user_roles`，实时拼出展示数据，**没有一张叫 `sunshine_ledgers` 的独立集合**，也没有任何 Webhook/事件驱动的自动写入逻辑。
- `components/yangshan-wall`（善缘墙组件）调用的正是 `getSunshineLedger`，消费 `latestDonorsMonthly` 数组（`{name, deedText, timeLabel, amount}`），数据源是雨花斋捐赠记录，**与工坊分账/`charity_contributions` 是两套完全独立、互不打通的展示系统**——第一部分图里"工坊分账 → 自动写入 sunshine_ledgers → 推送到 yangshan-wall"这条联动链路当前不存在。

## 三、目标设计 vs 现状差距清单

| 目标设计元素 | 当前现状 | 差距 |
|---|---|---|
| `tenantType` 三分类字段 | 不存在；实际是门店级 `orgType`（七值枚举）+ 租户级 `businessType==='live_factory'` | 需要新增字段或重新设计判定逻辑；且"雨花专区/民间斋堂"当前共享同一数据模型，二者合并需要先拆分 |
| `checkTenantPermission` 按 `tenantType` 分流永久旗舰版 | 该云函数完全不感知 `orgType`；雨花斋免费权益靠独立功能点豁免实现 | 需要新增鉴权分支；本次已明确决定暂不实现，需业务侧正式排期后再评估影响面（会把"文案豁免"升级为"鉴权豁免"） |
| `licenseCode` 公益共担码校验（民间斋堂多店） | 不存在民间斋堂与雨花斋的区分，也不存在与 `activationCode` 不同的第二套兑换码体系 | 需要先解决"民间斋堂"分类问题，再设计新的兑换码类型（或复用现有 `activateTenantSubscription` 体系加一个 `codeType`） |
| 微信原生分账 70/15/12/3 四方固定比例 | 真实是三方（工坊/推广/平台）可配置比例（默认 75/20/4.4/0.6），无固定"善款"份额 | 需要重新设计费率模型，新增第四个受益方角色，且要解决"公益基金池"没有真实分账收款商户号的合规问题（手册 2.7 节已指出这是原有设计特意规避的风险点） |
| `triggerSunshineLedger` 事件驱动、自动写入 `sunshine_ledgers` | 真实是读时聚合 `getSunshineLedger`，`charity_contributions` 是手动 pledge/redeem 记账，无自动化联动 | 需要新增独立集合 + 事件触发机制；且需要决定是否要把已有的 `charity_contributions` 手动流程改造成自动化流程，还是并行新建一套 |
| 善缘墙自动展示工坊分账反哺记录 | 善缘墙只读 `report_logs`（雨花斋捐赠），与工坊 `charity_contributions` 完全独立 | 需要新增聚合逻辑把 `charity_contributions` 的 `redeemed` 记录也纳入善缘墙展示源 |

## 四、伦理防火墙目标设计（2026-09-08 追加）

> 同第一部分的处理原则：以下是业务侧提出的伦理/机制构想，**逐条附现状核对**，不代表已落地。

### 4.1 伦理根基（构想，业务原则性表述）

- **雨花斋核心精神的绝对不可侵犯性**：精神图腾"拒绝杀戮、没有交易、只有感恩"；堂口铁律"就餐不收钱，堂内严禁设立任何形式的结算终端、购物车与收费入口"；平台对雨花全网门店永久免除一切软件费用与功能门槛。
- **现代百丈清规**：借唐代百丈怀海禅师"一日不作，一日不食"的农禅并重自养机制，破局"堂内不行买卖，堂外自立工坊"——工坊是雨花的"护法粮仓"，不是"附属商铺"。

### 4.2 四重物理防火墙架构图（构想）

|                  【第一重：空间物理绝缘】                                |
|  雨花爱心专区：纯粹记账、义工打卡、阳光公示（代码层彻底剔除交易接口）    |
+-------------------------------------------------------------------------+
                                    ▲
                                    │ (严格单向隔离：食堂内绝不卖货)
                                    ▼
+-------------------------------------------------------------------------+
|                  【第二重：堂外工坊自立】                                |

+-------------------------------------------------------------------------+
                                    │
                                    │ 纯物资平准定向结缘 (不见钱，只送粮油)
                                    ▼
+-------------------------------------------------------------------------+

### 4.3 逐重现状核对

- **第一重（空间物理绝缘）——已基本成立，可视为既成事实，不是待建目标**：全仓库核查雨花斋相关页面（`pages/index`、`pages/profile`、`subpackages/reports`），没有发现任何 `wx.requestPayment`/购物车/收银结算类交易接口——"结算"关键词命中的均是记账语境（如"结算门店流水"的账目派生文本），不是消费收单。雨花爱心专区从产品设计上就只有记账/打卡/公示，从未有过交易入口，"剔除交易接口"不需要额外动作。
- **第二重（堂外工坊自立·微信原生分账）——部分成立，默认关闭**：微信原生分账不是默认开启的，`tenants.settlementConfig.paymentMode` 只有 `'none'`（默认，人工/代理结算）与 `'direct_wechat'`（自动分账）两个真实取值，工坊需要主动配置成 `'direct_wechat'` 才会调用微信 Profit Sharing 接口；"无资金池/二清"这一合规特性只在 `'direct_wechat'` 模式下成立。
- **第三重（阳光反哺凭据·"功德受赠"实物化展示）——机制已有雏形，展示口径不一致**：真实的反哺记账是 `charity_contributions` 集合（`pledge`/`redeem`），但**金额单位是"分"（人民币），核销后在个人中心「产销工坊反哺」卡片展示为 `¥{{charityTotalYuan}}`（`profile.ts` 的 `charityTotalYuan = (total/100).toFixed(2)`）——是一个人民币金额，不是"大米 800 斤"这类实物折算展示**。要落地"只显示功德受赠、不显示金钱"，需要新增"金额 → 实物折算"的展示层转换（如按当期米价换算斤数），且要决定折算依据（哪张商品的单价、是否随行就市），当前完全没有这层转换逻辑。
- **第四重（消费者端白盒存证·自动映射 yangshan-wall）——不成立**：与第二部分 2.4 节结论一致，`yangshan-wall` 只读 `getSunshineLedger`（聚合 `report_logs`/`volunteer_duty_logs`），与工坊订单/`charity_contributions` 完全独立，不存在"买货扫码溯源 → 自动映射善缘墙"的联动链路，也没有任何订单详情页承载"本单利润已定向反哺"的溯源存证文案。这条需要新建：① 订单详情页的溯源展示，② 打通 `charity_contributions` → 善缘墙展示源的聚合逻辑（与第三部分差距清单最后一行是同一项待办）。
